## Noctalia shell (v5.3.0) on CachyOS/niri

- Config layering, learned the hard way on 2026-10-25: `~/.config/noctalia/config.toml` is declarative and loaded **first**; the GUI writes `~/.local/state/noctalia/settings.toml`, which is loaded **last and wins**. A GUI value silently overrides the config file — that is why `[desktop_widgets] enabled = false` in the state file killed the desktop clock even though config.toml said `true`.
- **The instrument for the merged truth is `noctalia config export`** (prints the effective config as TOML) and `noctalia config validate` (prints `✓ Config is valid`). Neither file alone shows what is live; read the export before concluding a setting "did not apply".
- Key ownership split as measured on 2026-10-25: the **GUI owns** widget lists, bar widget order, `box_width`/`box_height`/`cx`/`cy` of desktop and lock widgets, bar `font_scale`/`scale`/`padding`/`thickness`/`widget_spacing`/`reserve_space`/`compositor_blur`, dock `icon_size`/`item_spacing`/`main_axis_padding`/`layer`, theme and wallpaper. The **config file owns** what the GUI does not persist: bar `position`/`radius`/`margin_ends`/`margin_edge`/`background_opacity`/`shadow`/`capsule`, dock `radius`/`margin_*`/`cross_axis_padding`/`opacity`/`show_running`/`position`/`enabled`, `shell.polkit_agent`, `wallpaper.directory`, and widget `font_family`/`format`. So editing the big clock's size in config.toml does nothing — that key is in the state file.
- Theme state on 2026-10-25: `source = "wallpaper"`, scheme `m3-content`. `community_palette = "Oxocarbon"` is present but inert — it only takes effect when `source = "community"`. Palette files: `~/.local/state/noctalia/community-palettes/` (catalog at `.catalog/palettes.json`).
- Design references live in `~/Projects/noctalia-inspiration/` — `kirisaki.webp` is the reference shot, `index.html` is the contact sheet, `niri-noctalia-showcase/` the collected setups.
- **Desktop-widget sizing is measured, not guessed (2026-10-25):** the clock/date font size is driven by the widget box, and the rendered text fills the box width. Text width ≈ 7.6× the cap height for the clock (`05:46 PM`) and ≈ 15× for the date (`Sunday, 25 Oct 2026`). So growing the clock means growing **both** `box_width` and `box_height` in the same ratio — height alone clips, width alone shrinks the glyphs. Geometry history: started at 420×120 (too small), 840×240 was fine, 1150×300 was "way too big", settled at 760×217 — then **Ben moved it himself by dragging in the desktop-widget editor on 2026-10-26, to `clock_big` 896×384 at (1408, 700)**, `date_line` 460×61 at (960, 545). The live values live in the GUI state file, so a drag overwrites whatever the config file says.
- Screenshot verification trick when windows cover the desktop: `niri msg action focus-workspace 2` (empty workspace) shows the wallpaper layer with the widgets, then focus back. `noctalia msg desktop-widgets-toggle-edit` also renders an editor overlay above the windows, but not reliably across reloads.
- **The wallpaper follows the theme mode (2026-10-26), via a hook, not a native key.** Noctalia has per-mode *browse directories* (`directory_light` / `directory_dark`) but only one applied wallpaper path (`wallpaper.default.path`), so a `theme_mode_changed` + `started` hook runs `~/.config/noctalia/hooks/wallpaper-by-mode.sh`. Because the palette source is `wallpaper` (m3-content), the palette re-derives from the new image, so shell, kitty and wallpaper stay in one mode. `[[wallpaper.favorite]]` entries can carry a `theme_mode` + `palette_source`, but applying one is a manual picker click — there is no auto-apply-on-mode-change.
- **Each mode keeps its own wallpaper, and a manual pick is remembered (2026-10-26).** A hardcoded light→X / dark→Y mapping overwrote Ben's manual choice, which was the bug he reported: he picked a different light wallpaper, and switching back to light gave him the *old* one. The hook now keeps slots in `~/.local/state/noctalia/wallpaper-by-mode` (`light = "…"`, `dark = "…"`), and the slots are event-driven, not inferred: `wallpaper_changed` files the new picture under the current mode, `theme_mode_changed` (and `started`) restore that mode's picture. Inferring "whatever was on screen when leaving a mode" was a bug — the wallpaper applies ~1 s after the mode flips, so it saved the wrong mode's picture. Verified both directions: a manual light pick survives a dark round trip, and a manual dark pick survives a light round trip.
- **Measured cost of one theme-mode change (2026-10-26):** hook fires T+0, icon write + shell reload T+24 ms, wallpaper set T+84 ms, wallpaper texture uploaded T+173 ms, wallpaper-depth mask uploaded T+1.5 s, then Noctalia's own 1.5 s fade. So the machinery overhead is ~100 ms; everything past that is Noctalia's wallpaper path (the `wallpaper_depth` plugin re-uploads a depth mask per wallpaper, the biggest single cost). **Do not measure this by polling the IPC in a loop** — each `noctalia msg` spawn queues behind the busy shell and the loop reports seconds that never happened; use the log timestamps instead.
- **Theme-mode button on the bar (2026-10-26):** the built-in `theme_mode` widget renders a **fixed half-circle glyph in both modes** in this build (not the moon/sun the docs describe), so it cannot show which mode is active. The working setup is a `custom_button` named `theme_cycle` whose glyph is rewritten by `~/.config/noctalia/hooks/theme-glyph.sh` — sun (light), moon (dark), sun-moon (auto) — and whose left click runs `~/.config/noctalia/hooks/theme-cycle.sh` to cycle light → dark → auto. Two things that cost real debugging time: **`theme_mode_changed` only fires when the *resolved* mode changes** (so light → auto never fires it, because auto resolves to light — the cycle script therefore sets the icon itself), and the configured mode must be read from `~/.local/state/noctalia/settings.toml` (`[theme] mode`) because `noctalia msg theme-mode-get` reports only the resolved mode. Noctalia has no runtime setter for a widget glyph and no `bar-reload`, so changing the icon means rewriting one line of config.toml and calling `config-reload` (measured 100–300 ms).
- Noctalia's icon names come from `/usr/share/noctalia/assets/fonts/tabler.json` (5958 Tabler glyphs) — plain Tabler names like `sun`, `moon`, `sun-moon` work; Noctalia aliases like `night-light` do not exist and log `missing glyph`.
- `auto` mode needs `[location]` coordinates (or a custom sunrise/sunset schedule). **Set on 2026-10-26: `[location] latitude = 5.6037, longitude = -0.1870` (Accra, Ghana)** — manual coordinates, so no IP lookup and no geocoding request. The machine's timezone is already `Africa/Accra`. Proof the schedule is actually consulted: injecting a temporary `custom_schedule` with `sunset = "09:00"` / `sunrise = "11:00"` flipped `auto` to **dark** at 10:05; removing it returned to **light** (computed daytime). Until then, `auto` had no schedule and always resolved to light.
- **Noctalia v5 docs live at `docs.noctalia.dev/noctalia`** — widget pages under `/noctalia/bar/widgets/<name>/`, config pages under `/noctalia/configuration/`, desktop widgets under `/noctalia/desktop/widgets/`. `noctalia.dev` is the marketing site; its `/docs` path returns 410. The v5 shell is a compiled C++ binary (no QML on disk), so `strings /usr/bin/noctalia | grep <widget>` is the way to confirm a widget exists in the installed build.
- Bar widget placement is per-instance `start` / `center` / `end` lists in `[bar.<name>]`. Two easy-to-confuse widgets: **`tray`** shows StatusNotifierItem icons (background apps) — the shell itself hosts `org.kde.StatusNotifierWatcher`, so any SNI app registers with it (Steam does; `pavucontrol` does not, it is legacy XEmbed), and **`taskbar`** shows running + pinned app icons. Ben asked for the tray (2026-10-25); the taskbar was tried and fully reverted.
- **The terminal is kitty (0.49.2); foot was removed on 2026-10-26.** `/usr/bin/x-terminal-emulator` is a plain symlink to `/usr/bin/kitty` — the `alternatives` package does **not** exist in these repos (pacman: "target not found"), so update-alternatives is not an option and the symlink is the mechanism. That covers the `Terminal=true` apps (micro, btop, vim). The deciding measurement: a standalone foot does **not** re-read its config on SIGHUP (changed the file on disk, sent SIGHUP to a live foot — the window kept the old colours), while kitty reloads on SIGUSR1, and Noctalia's kitty template ends with exactly that: `/usr/share/noctalia/assets/templates/kitty/apply.sh` finishes with `pkill -USR1 kitty`. So the bar, panels and terminal now change palette together.
- **The theme-mode button is a local plugin, not shell scripts (2026-10-26).** `~/.local/share/noctalia/plugins/theme-switch/` (the built-in *local* source — it runs in place, so editing a `.luau` file hot-reloads it). Two entries: a **widget** (the button) and a **service** (the wallpaper-per-mode logic). That split is forced by the API: a widget entry is *not* restarted when the shell config changes (only a service gets `onConfigChanged()`), so the wallpaper logic has to live in the service or it never runs. The click still costs one subprocess (`noctalia msg theme-mode-set`) because the runtime API has no in-process setter for the theme mode. The slots live in the plugin's data dir: `~/.local/state/noctalia/plugins/data/ben/theme-switch/state.toml`.
  - Driving the button without a pointer: `noctalia msg plugin ben/theme-switch:button all cycle` — note the **target comes before the event** (`plugin <id> <target> <event>`), and the target is `all`, not the bar name.
  - Editing `plugin.toml` does **not** re-read the entry list; disable + enable the plugin to pick up manifest changes.
  - A cycle can be silently lost if it lands while the plugin is being re-materialized (the dispatch hits a torn-down runtime). Retrying works.
- **Neither a widget nor a service gets an event for shell-level config changes** (measured 2026-10-26 with a marker log): `onConfigChanged()` fires only for the plugin's *own* settings, and a widget entry's runtime is **not** recreated when the shell config changes (the bar is rebuilt, the entry is not). So the shell's own `[hooks]` events are the only true trigger — and they call the plugin over IPC instead of spawning scripts:
  ```
  [hooks]
  theme_mode_changed = "noctalia msg plugin ben/theme-switch:wallpapers all sync"
  wallpaper_changed  = "noctalia msg plugin ben/theme-switch:wallpapers all sync"
  started            = "noctalia msg plugin ben/theme-switch:wallpapers all sync"
  ```
  Zero polling, zero script files, and the work itself (reading the mode, applying the wallpaper) stays in-process. The wallpaper IPC-from-hook path does not deadlock — proven many times.
- **Measured gains from the rewrite (2026-10-26):** a mode change went from ~950 ms to the wallpaper changing and ~465 ms to the texture being uploaded (was ~1.5 s), because the depth plugin's per-wallpaper mask work is gone. The cross-fade is 500 ms now (`transition_duration`). The old path cost three shell scripts, two config writes and two full shell reloads per mode change; the plugin costs one subprocess (the theme-mode setter — the runtime API has no in-process setter for it) and nothing else.
- **Audit of the rest of the machine (2026-10-26):** the 4.4 GB `/var/cache/pacman/pkg` is 4.55 GB of *currently installed* packages (the offline rollback net) — only 0.10 GB is stale versions, so `pacman -Sc` would free ~100 MB and `pacman -Scc` would trade rollback for 4.5 GB on a disk with 124 GB free. **Left alone deliberately.** Xwayland holds 91 MB with zero X11 clients, but `ELECTRON_OZONE_PLATFORM_HINT=auto` in niri's env means an Electron app that cannot do Wayland falls back to X11 — not worth 91 MB on a box with 3.9 GB free, **left on deliberately.** niri's animations are springs (not eases) and its blur is already at 2 passes (default 3). No user timers, no cron. Biggest RAM users: opencode 948 MB (the agent itself), BrowserX 174 MB (Ben's own browser-bridge daemon + MCP), kitty 151 MB, niri 126 MB, tailscaled 54 MB — 1800 MB of 7253 MB used, 3950 MB free.
- **Audit of Noctalia's own behaviour (2026-10-26), measured:**
  - `wallpaper_depth` plugin **disabled**: it changed only 168 of 130,000 pixels in the clock's area on both wallpapers (the clock at x=1408 sits over sky/clouds, not scenery) while costing 0.5–1.5 s of background CPU per wallpaper change plus a 99 MB model and a Python venv. Re-enable with `noctalia msg plugins enable noctalia/wallpaper_depth`.
  - `shell.offline_mode = true` — every launch and config reload was burning a DNS timeout on the community catalogue (16 failures in the log). The palette is wallpaper-derived and the kitty template is local, so nothing needs the network.
  - `[wallpaper] transition_duration = 500` (was 1500) — the cross-fade was the dominant *visible* cost of a mode switch.
  - The bluetooth connect churn (2–4 D-Bus timeouts a minute, one blocking 25 s) was **transient**: 0 failures in 150 s both with and without the bluetooth widget. The AirPods and the Wireless Controller go out of range; the shell retries them, bluez does not.
  - The `~/.face` decode warnings stopped at 10:16 and the path no longer exists — historical, not live.
  - A mode change still costs ~950 ms end to end: ~70 ms is the wallpaper itself, the rest is Noctalia's own theme apply plus the config reload its own mode-persistence triggers. That reload is the event hook the plugin service rides on — Noctalia's config watcher fires on any change to `~/.config/noctalia/*.toml` or `settings.toml`.
- Theme wiring for kitty: `[theme.templates].builtin_ids = ["kitty"]` (GUI state file) makes Noctalia write `~/.config/kitty/themes/noctalia.conf`; `~/.config/kitty/kitty.conf` includes it. `[theme].mode` is `dark|light|auto`, where `auto` follows the sunrise/sunset schedule in `[location]`; `sync_color_scheme = true` (default) also writes `org.gnome.desktop.interface color-scheme` so GTK/Qt/Electron apps follow the same mode. Verified live on 2026-10-25: kitty's background went light (99% white) → dark (12%) → light again across `noctalia msg theme-mode-set dark|light`.
- foot facts worth keeping if it ever comes back: SIGUSR1/SIGUSR2 switch a running foot between `[colors-dark]` and `[colors-light]` (verified — SIGUSR2 flipped a live terminal from red to blue); `footclient` has no `--config`, so in server mode the **server** owns the config (socket `$XDG_RUNTIME_DIR/foot-$WAYLAND_DISPLAY.sock`) and a live-reload setup needs `foot --server` plus SIGHUP to the server. And **in foot an included file's section beats the including file's own section of the same name** — the Noctalia include's light palette rendered even while foot.ini still carried its Catppuccin `[colors-dark]`.
- Bar instances are named subtables `[bar.<name>]`, and the default instance is **`default`** — not `main` (the docs' example uses `[bar.default]`). Declaring `[bar.main]` creates a *second* bar instead of restyling the first, and stale instances survive until the shell restarts. The live bar here is named **`nock`** (created in the GUI).
- `desktop_widgets.widget.<id>.scale` **does not exist in 5.3.0** — the shell logs `unknown setting`. Size widgets with `box_width`/`box_height` instead. Likewise `grid.center_guides_visible` and `grid.snap_to_center` are unknown in this build.
- `[dock]` needs an explicit `enabled = true`; without it the dock silently disappears (it is not enabled by default).
- Shell log lives at `~/.cache/noctalia/noctalia.log` — the journal has nothing for it. Grep it for `WRN`/`ERR` after every config change; that is where "unknown setting" warnings surface.
- Lock screen: `[lockscreen] wallpaper = "<path>"` (empty = use the desktop wallpaper). Lock screen widgets are a separate `[lockscreen_widgets]` section, and the built-in `login_box` widget is what provides the password field — do not remove it.
- Greeter: `greetd` + `noctalia-greeter` (both in the CachyOS repos). `display-manager.service` now points at greetd; **SDDM is disabled but still installed** as the fallback, with the fingerprint PAM line migrated to `/etc/pam.d/greetd`. `noctalia msg greeter-sync` copies wallpaper/palette to the login screen.
- Boot safety backup (2026-10-25): `~/backups/boot-20261025-032036/` holds `limine.conf`, both EFI binaries, the splash, `/etc/default/limine`, `fstab`, the package list, and a `RESTORE.sh` that puts them back.
