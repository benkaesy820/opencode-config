## republicmart-rust — the Rust v2 backend (new, 2026-10-26)

- 2026-10-26: Ben decided to build **republic-mart's backend again in Rust**, as a greenfield rebuild of the same product domain, not a port of the TypeScript backend ("assume the TS one doesn't exist"). The dominant goal is **footprint**: the service must fit the Northflank box (0.1 shared vCPU, 256 MB). The repo directory `~/Projects/republicmart-rust` was created empty on 2026-10-26.
- 2026-10-26: **the database stays Turso** (remote libsql), accessed from Rust. The current production DB is already Turso (`TURSO_DATABASE_URL` + `TURSO_AUTH_TOKEN`), so the container is stateless and carries no DB file — the Rust service inherits that model, with no volume needed.
- 2026-10-26: **the Rust client path is proven, not assumed.** `libsql` 0.10 (features `remote,tls`, i.e. **no `core`/libsql-sys and therefore no C compiler and no bundled SQLite**) speaks the Hrana **v3 pipeline** API. Verified end to end on this box: a Rust binary connected to a local Turso server, created a table, inserted a row and read it back (`sqlite_version=3.45.1`). That binary, stripped, is **4.88 MB** — the whole client stack. `Builder::new_remote(url, token)` + `.namespace(db_name)` is the Turso Cloud form; `sql` is `execute(sql, params)` and `query(sql, params)` both take params in 0.10.
- 2026-10-26: **local development is a plain SQLite file, not a Turso server** (Ben's decision, 2026-10-26). `sqld` 0.24.32 and `tursodb` 0.8.3 were uninstalled; only the `turso` management CLI remains. Local SQL goes through `/usr/bin/sqlite3` (3.54.0, installed). `turso db shell` **cannot open a local file** — the Rust CLI's local shell is a Go binary built with `CGO_ENABLED=0` and fails with "go-sqlite3 requires cgo to work"; `turso db shell` still works against cloud databases. A local file is pushed to Turso with `turso db import` (which has a `--tursodb` flag for an MVCC database).
- 2026-10-26: **"Rust SQLite" is not a faster SQLite.** `rusqlite`, `sqlx` and `libsql`'s local mode are Rust *bindings* to the C engine and run at the same speed as the `sqlite3` CLI; the only pure-Rust SQLite-compatible engine is Turso's VDBE, which is what Turso Cloud runs. Embedded file access beats a remote server per query by one to two orders of magnitude (10–100 µs vs a network round trip), so the split is: file for development, remote Turso in production, same `libsql` crate and same SQL dialect on both sides.
- 2026-10-26: **a musl-static build needs a musl C toolchain** — `ring` (under rustls) and `libsql-sqlite3-parser` both go through `cc-rs`, which fails with `failed to find tool "x86_64-linux-musl-gcc"`. Fix: `pacman -S musl` and set `CC_x86_64_unknown_linux_musl=musl-gcc`, or use `cargo-zigbuild`. The cheaper answer: build for glibc and use `gcr.io/distroless/cc-debian12` — **image size is disk and pull time, RSS is what the 256 MB box actually feels**, so a glibc base costs nothing that matters.
- 2026-10-26: the Turso **management CLI is `tursodatabase/turso-cli` v1.0.34**, installed at `~/.local/bin/turso` (`db list|create|shell|tokens|branch|locations|import`, `dev`, `auth`). It is a *different* binary from the `tursodatabase/turso` release assets, whose `turso_cli-*.tar.xz` actually contains only the embedded shell `tursodb`. `turso dev` shells out to `sqld` and fails without it on PATH — not needed now that development uses a plain SQLite file.
- 2026-10-26: `get.tur.so` (the official Turso install script) is **TLS-intercepted on this network** — the chain comes back from a Fortinet device (`CN=FG4H1FT924902450`) and that root is not in the system CA store, so curl fails with "unable to get local issuer certificate". github.com, crates.io and example.com all present normal public CAs, so the interception is selective. **Do not fetch installers through it**; take GitHub release binaries and verify the published sha256 instead (done for both turso-cli and sqld).

- 2026-10-26: **measured footprint comparison, same day, same box.** The TypeScript backend, run locally from `backend/dist` against its Turso dev database (`aws-eu-west-1`): **RSS 144 MB idle, peak 317 MB** (`VmHWM`), 11 threads, and `/api/products` took **2.04 s** for a 22 KB response (N+1 queries across the network to Ireland). The Rust equivalent stack, built and run on the same box: **RSS 11.1 MB steady, 29.9 MB peak**, 2 threads, **7.72 MB** single binary (6.92 MB with `panic = "abort"`), cold start to first `/healthz` 577 ms. That is a 13x memory difference — and the TypeScript peak of 317 MB is **above the 256 MB Northflank limit** the service is supposed to run on, so the current backend does not fit its own box. Check the Northflank memory graph for the live service.
- 2026-10-26: `panic = "abort"` saves 0.8 MB of binary and 0.5 MB of RSS but **kills the whole process when a background task panics** (proved: a failed DB connect in a spawned task aborted the service). Use `panic = "unwind"` plus `tower-http`'s `CatchPanicLayer`; the cost is 0.8 MB.
- 2026-10-26: **`reqwest`'s `rustls-no-provider` needs the crypto provider installed at startup** (`rustls::crypto::ring::default_provider().install_default()`) or the first TLS client panics. Choosing `ring` over `aws-lc-rs` avoids needing cmake, which is not installed on this box. `metrics-exporter-prometheus`'s **default** features pull `push-gateway` → `hyper-rustls` → `aws-lc-rs` → cmake, so it must be `default-features = false, features = ["http-listener", "async-runtime"]`.
- 2026-10-26: API changes worth knowing in the chosen crates: **rand 0.10 renamed `OsRng` to `SysRng`**; **argon2 0.6 replaced `hash_password(pw, &SaltString)` with `hash_password_with_salt(pw, &[u8])`** and gained `hash_password_into_with_memory`, which lets the caller supply the memory blocks — a fixed 16 MiB buffer that is allocated once and reused, so peak RSS is predictable under a login flood; **axum-extra 0.12 exposes `CookieJar`**, not a `Cookie` extractor; **clap 4** needs the `Parser` trait in scope for `Cli::parse()`.

- 2026-10-26: **Phase 0 is done and committed** in `~/Projects/republicmart-rust` (git repo, branch `main`, first commit `4c441b1` "Phase 0: the footprint gate"). A cargo workspace with one member `crates/api` (axum on a 2-worker tokio runtime, `/healthz`, JSON logs, graceful shutdown on SIGTERM/SIGINT), `tools/footprint.sh` as the gate, a Makefile and a CI workflow that run the same checks in the same order, and a Dockerfile building on `rust:1.99.1-slim-bookworm` for `gcr.io/distroless/cc-debian12`. Measured: **1.79 MB binary, 4.1 MB resident, 14–28 ms cold start** against budgets of 8 MB / 40 MB / 150 ms.

- 2026-10-26: the container must be built **inside** the Dockerfile. The local box is CachyOS with glibc 2.44; `distroless/cc-debian12` is Debian 12 with glibc 2.36, so a locally built binary dropped into that image would not run.

- 2026-10-26: the repo is split into **`backend/`** (the Rust service) and **`frontend/`** (the storefront, not started), with a thin root Makefile that delegates. The Rust project lives entirely under `backend/`, including its own `Cargo.toml`, `Makefile`, `Dockerfile`, `deny.toml`, `rust-toolchain.toml`, `vendor/` and `.cargo/config.toml`.
- 2026-10-26: **the Turso client is not `libsql`.** `libsql` 0.10's remote path is built on hyper 0.14 / http 0.2, and its `tls` feature pins `rustls-webpki` 0.102, which carries RUSTSEC-2026-0104 and RUSTSEC-2026-0382 with no fix reachable from that chain (rustls 0.22 requires webpki ^0.102). Turso's own `turso` crate 0.8.3 was measured and rejected: it embeds the whole engine (`turso_core` compiles to an 85.5 MB rlib). **Decision: talk to Turso's documented HTTP pipeline API with `reqwest`**, so the service has exactly one TLS stack (rustls 0.23.46 on rustls-webpki 0.103.16), and run development and tests against a normal SQLite file with `rusqlite` 0.40 + `tokio-rusqlite` 0.8 (bundled SQLite).
- 2026-10-26: `web-push` was **cut** from the dependency set: it reaches `rsa` (RUSTSEC-2023-0071, the Marvin attack, no patch) and `crypto-bigint` (RUSTSEC-2026-0374 / -0387, no patch) through `jwt-simple`. It was already a v2.1 feature. The only remaining ignore is RUSTSEC-2026-0374 for `basic-toml`, an **unmaintained but not vulnerable** build-time dependency of askama's derive macro.

- 2026-10-26: **Phase 1 is done** in `~/Projects/republicmart-rust/backend`: the data layer, the migration runner and the event bus. `crates/api` is now a **library plus a thin binary** (`src/lib.rs` + `src/main.rs`), so the media worker later reuses it. The data layer is one enum, `Database::Sqlite` / `Database::Turso`, with no trait objects, no `async-trait` and no boxing; the same test suite runs against both engines, and the live Turso tests are skipped without credentials. Files: `db/mod.rs`, `db/turso.rs`, `db/sqlite.rs`, `db/migrate.rs`, `db/tests.rs`, `events.rs`, plus `build.rs` embedding `migrations/`.
- 2026-10-26: **Turso sends blobs as base64 *without* padding** (`"AQI"`, not `"AQI="`), so the decoder accepts both (`DecodePaddingMode::Indifferent`). The first version silently turned a failed blob decode into NULL — a data-loss bug that the live test caught; the decoder now returns a protocol error instead of a quiet null.
- 2026-10-26: `reqwest` 0.13's **default retry policy only retries low-level protocol NACKs**, never transport errors, so it cannot silently re-send a write. That is the HTTP-level enforcement of the "the server never retries" decision.
- 2026-10-26: trimming three unnecessary `reqwest` features (`gzip`, `http2`, `charset`) took **1.1 MB and eight crates** out of the binary. The binary is now **6.12 MB**, resident memory **5.9 MB**, cold start **11–30 ms**. The binary budget was raised from 8 MB to **10 MB** with the reasoning recorded: the binary is disk, the box has 124 GB free, so the binary limit is a bloat tripwire and the **40 MB resident limit is the real constraint**.
- 2026-10-26: **the `turso` crate (Turso's own Rust SDK) was measured and rejected on footprint.** A hello-world that only opens an in-memory database and inserts one row produces a **14.40 MB** stripped release binary, and takes **5m09s** to build cold. The whole republic-mart API with every feature (axum, tokio, reqwest, rusqlite, image, argon2, askama) is **2.43 MB** and builds in 1m52s. The SDK embeds Turso's SQLite-compatible engine, and its remote mode is a synced local replica rather than a stateless remote client. The Turso client in this project is therefore a thin HTTP-pipeline client over `reqwest` — the same API every official Turso client speaks — and the 8 MB budget stands. Ben approved this on 2026-10-26 ("so far as its fast and reduce overhead and efficient then that perfect").
- 2026-10-26: **the write policy, decided 2026-10-26: honest outcomes plus idempotency keys — never a blind retry, never a refused write on a protected path.** The data layer's `transaction()` returns one of four outcomes, never collapsed into a generic error: **Committed** (every step ran, the COMMIT step executed), **RolledBack** (a step failed, the ROLLBACK step executed, the COMMIT was skipped), **NotApplied** (the request never left the box — a connect failure, so nothing was sent), and **Unknown** (the request was sent and the outcome is genuinely undetermined: a timeout, a broken write, or a lost response). `Unknown` is never reported as a rollback and never retried inside the server.
- 2026-10-26: **why the server never retries:** a 0.1 shared vCPU box should not spend its CPU re-sending a request while the network is already failing; the retry belongs to the client, and it is only safe because of the idempotency key. Every money-path write carries a client-generated key stored in the same transaction (a UNIQUE constraint on an idempotency table), so a retry after `Unknown` either commits once or returns the original result. A write path **without** an idempotency key must fail closed on `Unknown` — that is the one rule that protects the paths that cannot be retried.
- 2026-10-26: the reference implementation was read to settle the transaction design: Turso's own `@libsql/client` 0.18.0 (`hrana.js`) uses a **dedicated stream** plus `BEGIN`, then `COMMIT`/`ROLLBACK` in a **separate later request** — two round trips, a server-side stream and a write lock held across the wire. The Hrana 3 spec names the alternative: *"Clients can use this mechanism to implement non-interactive transactions in a single roundtrip"* — the conditional batch. Ours uses the conditional batch (one request), and **verifies the response** rather than trusting it: the outcome is read from which of the ROLLBACK/COMMIT steps actually ran.
- 2026-10-26: **Turso's HTTP pipeline is NOT atomic — measured, not assumed.** A pipeline of `execute` requests runs every statement even when one fails, and the failed statement leaves the earlier writes committed. A `batch` request is no better: it reports per-step `step_errors` but still commits the successful steps. `BEGIN` + a failing statement + `COMMIT` in one pipeline also commits the earlier writes. The only one-round-trip atomicity that works is a `batch` whose steps carry conditions. **The trap:** `BEGIN` + statements with **no** `COMMIT` does not commit, but it leaves an open transaction on the server holding locks until the server reaps the stream — never do that.
- 2026-10-26: the Hrana v2 protocol details that matter: values are `{"type":"null"|"integer"|"float"|"text"|"blob"}` with integers as **strings** and blobs base64-encoded; `last_insert_rowid` is a string; `want_rows` defaults to true; `baton: null` creates a new server-side stream per request, so one HTTP request is one unit of work with no server-side state to leak. `store_sql` is per-stream, so it is useless without a long-lived baton.
- 2026-10-26: **Phase 2's schema is written and applied** — seven migration files in `backend/crates/api/migrations/`, one per domain, each applied in a single transaction. **43 tables, 78 indexes, 6 triggers** against the old system's 63 / 199 / 66. The old schema's foreign keys were **never enforced** (`PRAGMA foreign_keys` was 0 on the production database, so every `ON DELETE RESTRICT` was decorative); the first migration turns the pragma on, which on Turso is a **database-level setting that persists** (verified: it stuck across separate connections, and `dom-mart` is still 0).
- 2026-10-26: the ledger convention, decided and stated once: **an amount is the signed change in an account, a debit being positive, and every posting sums to zero.** A positive `platform_cash` is cash held, a negative `seller` is money owed to that seller, a negative `revenue` is income earned. Account kinds: `platform_cash`, `buyer`, `seller`, `revenue`, `commission`, `payable_buyer`.
- 2026-10-26: the migration splitter has to understand SQLite's `BEGIN ... END` trigger bodies (a semicolon inside a body does not end the trigger) and must skip comment-only chunks — a semicolon in a prose comment broke the first attempt, and a `CASE ... END` inside a body is counted as a nested block. Both are covered by tests.
- 2026-10-26: **the schema is prepared in the background, not before serving.** The gate caught this: running the migrations before the listener opened pushed the cold start to 1.7 s, because each migration against a remote database is a round trip. Now the listener opens first, `/healthz` answers in 11 ms, and `/readyz` stays red with a reason until the schema is the one the build expects. A slow or unreachable database must never stop the container booting.
- 2026-10-26: **the old republic-mart database is `dom-mart`** (the old backend's `.env` points at `turso://dom-mart-benkaesy.aws-eu-west-1.turso.io`). It holds **64 tables, 199 indexes and 66 triggers**. Crucially, **its status columns are plain TEXT with no CHECK** — the state machines lived in the TypeScript (`backend/src/domain-state.ts`, `delivery-state.ts`), so the database would have accepted any string as a status. The states had to be read from the code, not the schema.
- 2026-10-26: **the recovered state machines** (now in `backend/docs/domain.md` and enforced by the new schema): order = open/paid/delivered/completed/cancelled/disputed; delivery = 12 states (awaiting_seller_handover, received_by_platform, queued, assigned, out_for_delivery, delivered, seller_no_show, delivery_failed, returned, seller_collected, return_overdue, cancelled); money = awaiting_payment/pending/released/expired/cancelled/refund_pending/refunded/**exception**; listing = listed/reserved/sold/closed; moderation = pending/approved/rejected/changes_requested; seller capability = active/restricted/suspended/revoked. Two edges exist for operations, not the happy path: `assigned → queued` and `out_for_delivery → queued` re-dispatch a delivery stuck with a courier.
- 2026-10-26: **the money rules, recovered from `orders/service.ts`**: delivery fee = the **buyer's** zone base fee + `min(quantity − 1, 10)` × per-unit fee + a bulky handling fee (the cap of 10 exists so one large order shares one delivery run); service charge = `ceil(item_amount × bps / 10_000)`, capped at 1,000 bps (10%), charged on the **item amount only**, never the delivery fee; total = item + delivery + commission; currency always GHS. A buyer may hold **5 open orders** (the anti-reservation-griefing guard) and at most **100 units** of one product. The service charge is read from the settings on every quote, with the settings write invalidating the cached value.
- 2026-10-26: **the trust and safety system** is real and was missing from the first schema: seller applications, policy cases (severity minor/major/critical, status open/decided/appealed/overturned/dismissed, outcome no_action/warning/strike/listing_restricted/seller_suspended/listing_revoked), strikes, appeals, and a `policy_snapshot_json` carrying the policy version, the 365-day strike window, the 3-point listing restriction and the 14-day appeal window. The seller's listing capability is *computed* from it, never edited.
- 2026-10-26: **the `exception` rule**: a verified charge can arrive after the reservation expired or the order was cancelled, and must go to `exception` for an operator rather than being discarded or silently applied. The old code says so in a comment, and the new schema's payment states carry it.
- 2026-10-26: **the staff model, corrected.** The old product had **19 fine-grained capabilities** (`admin.control_plane`, `marketplace.moderate`, `dispute.read`, `dispute.review`, `payout.approve`, `delivery.assigned`, …) across 11 workspaces, bundled into named sets (`operations`, `operations+platform_store`, `courier`, `marketplace_moderator`). My first model — a role and two booleans — could not express "who may read a dispute versus who may resolve one". Now: `src/auth.rs` holds the roles, the 19 capabilities and the rule that **a role carries a default set in code**, while `staff_capabilities` holds only the extra grants with their expiry. Ben's role list (superadmin, republic staff with or without store management, admin, courier) maps onto that.
- 2026-10-26: **a seller is not a role — it is a business** (name, slug, legal name for the payout, a listing capability the trust system can withdraw, its own share codes). A user may be buyer, seller, courier and staff at once.
- 2026-10-26: the admin desks (`admin/routes.ts`, `audit/routes.ts`, `trust/routes.ts`, `delivery/routes.ts`) were read to check the schema serves them. Three gaps found and closed: the seller-unavailable queue on the order, the **audit retention** subsystem (holds + archives + the archive membership, with a hold as a *rule* rather than a frozen list), and a `(status, id)` index on every table a desk lists by status.
- 2026-10-26: **the money rules, recovered from the old product and written into `backend/docs/domain.md` to be confirmed by Ben** (they are product decisions, not schema ones). A refund is **manual and whole** — no partial, no automatic; provider refunds stay off until a Moolre refund contract is configured. A refund is refused in three cases: the order has moved past the point where it can be cancelled, the seller has already been paid, or a refund already exists for that transaction. **A refund cancels a pending payout in the same transaction with a compare-and-swap on the payout's status**, so the seller cannot be paid after the buyer was refunded. A dispute resolution **does not move money** — the old product refused to accept an amount on one on purpose. The windows (reservation timeout, handover window, dispute window, money-back days) are settings, not constants. The audit trail's retention classes are `routine`, `financial`, `protected`.
- 2026-10-26: **the role model, settled and written down in `backend/docs/roles.md`.** Six kinds of person: buyer, seller, courier, republic staff, admin, superadmin. A buyer is the absence of a role; a **seller is a business, not a role** (name, slug, legal name for the payout, a listing capability the trust system can withdraw, its own share codes); the staff have a role plus capabilities. **The Republic's own store is not a special thing — it is a seller like any other**, its id held in the settings, run by staff acting through the seller scope rather than through staff powers.
- 2026-10-26: **editing is guarded by a `version` column** on every row a person edits (10 tables): the API hands it out as an `ETag` and takes it back as `If-Match`, and a version that has moved is a **409, never a silent overwrite**. Rows that move through a state machine (orders, deliveries, disputes, payments) carry no version — the machine is the guard.
- 2026-10-26: **Phase 2's schema is now 54 tables, 115 indexes, 6 triggers, 94 enforced foreign keys** (the old product: 64 tables, 199 indexes, 66 triggers, and foreign keys that never fired). The migration history is squashed while the schema is still moving; it is frozen before the first real deployment.
- 2026-10-26: **the two commercial decisions are made (2026-10-27): the buyer pays the service charge, and the marketplace delivers** (it receives the goods from the seller, hands them to a courier, and records what the delivery cost — so the delivery fee it collects is its own until the courier is paid, and the margin on a delivery is the fee less the cost). Both were already the domain's defaults. The old product charged the commission **both ways** and kept it twice; the new ledger cannot express that.

- 2026-11-01: **decision — one SSE stream per tab stays; not one per browser.** Ben asked whether tabs should share a stream.
